# 23. Roadmap and Pilot Plan

This chapter sets out how to move the board from concept to routine practice. It covers the five-phase roadmap, a pilot charter for trialing the board on a [fictional or real] engagement, success criteria, governance, risks, and the decision requested. Use it as the basis for the conversation with your director and sponsor.

The principle behind the roadmap is the same as the advice for individual use: start simple, then expand. Prove value with one advisor before you rely on ten, and prove the board works with prompts before you invest in orchestration.

## The five-phase roadmap

| Phase | Timing | Focus | Main output |
|---|---|---|---|
| 1 Define and configure | Now | Build the board's foundations | Ten personas, charter, response standard, Context Brief |
| 2 Test the specialists | Now | Prove each advisor works alone | Passing test logs for all ten personas |
| 3 Test collaboration | Next | Prove advisors work together | Passing cross-advisor scenarios |
| 4 Establish reusable assets | Next | Make the board repeatable | Templates, scorecards, exemplar deliverables |
| 5 Introduce orchestration | Later | Automate where value justifies it | Business case and design, if approved |

### Phase 1: Define and configure (Now)

**Activities**

- Finalize the ten advisor personas, each with all eight elements: professional identity, mission, scope and boundaries, decision-making lens, core capabilities, deliverables, personality and challenge style, and operating rules.
- Finalize the Board Operating Charter: principles, collaboration rules, conflict rules, decision support, and data handling.
- Finalize the nine-section response standard.
- Finalize the Client Change Context Brief template.
- Confirm the approved tool environment and data-handling rules with firm policy owners.

**Outputs**

- Versioned persona configurations (v1.0)
- Charter, response standard, and Context Brief template (v1.0)
- Data-handling guidance for users [aligned to firm policy]

**Exit criteria**

- [ ] All ten personas include all eight elements, with element 8, operating rules, explicit.
- [ ] Charter and response standard reviewed by [reviewer role].
- [ ] Tool environment approved for intended use.

### Phase 2: Test the specialists (Now)

**Activities**

- Run the eight test scenarios for each persona (see Chapter 21).
- Score each test for Quality, Consistency, and Practical value.
- Fix failures, version the changes, and retest.

**Outputs**

- Test log per persona
- Board-level summary of readiness by persona
- Change notes for each persona revision

**Exit criteria**

- [ ] Every persona scores 3 or above on all measures across all eight scenarios.
- [ ] No automatic failures, such as fabricated facts or scores, in current versions.
- [ ] A second reviewer has scored a sample of tests.

### Phase 3: Test collaboration (Next)

**Activities**

- Run the cross-advisor tests: resistance, readiness gaps, and a difficult go-live.
- Test the Board Chair's synthesis and conflict-resolution behavior.
- Test the key handoffs, such as Change Impact to Training and Readiness, and personas to Communications.
- Run an end-to-end simulation of the first 30 days on the fictional ERP client (see Chapter 19).

**Outputs**

- Cross-advisor test log
- Revised charter collaboration and conflict rules, if needed
- End-to-end simulation output and lessons learned

**Exit criteria**

- [ ] All cross-advisor tests pass on the rubric.
- [ ] Deliverables in the simulation use consistent assumptions throughout.
- [ ] The Board Chair resolves conflicts explicitly rather than blending them.

### Phase 4: Establish reusable assets (Next)

**Activities**

- Build a library of templates for signature deliverables.
- Create scorecards for testing and for reviewing live outputs.
- Curate exemplar deliverables from the fictional ERP simulation and, with permission and full anonymization, from pilot work.
- Keep client-specific information separate from generic templates at all times.
- Set ownership and a review cadence for the library.

**Outputs**

- Template library, scorecards, and exemplars [location]
- Prompt library and persona configuration pack
- Asset ownership and version control rules

**Exit criteria**

- [ ] Every asset has an owner and a version.
- [ ] No client-identifying information exists in any generic asset.
- [ ] At least [number] practitioners have used the assets and given feedback.

### Phase 5: Introduce orchestration (Later)

**Activities**

- Assess whether autonomous delegation, parallel execution, persistent shared artifacts, automated handoffs, or scheduled monitoring would add enough value to justify the effort and risk.
- If they would, define requirements, data protections, and human checkpoints.
- Pilot any orchestration on fictional data before live use.

**Outputs**

- Value assessment and recommendation: proceed or do not proceed
- If proceeding, a design and a separate pilot plan

**Exit criteria**

- [ ] Decision made by [decision owner], based on evidence from phases 1–4.
- [ ] Human-in-the-loop checkpoints preserved in any design.

> **Watch out:** Orchestration is introduced only if value justifies it. Automating a board that has not passed phases 2 and 3 automates its weaknesses.

### Objectives

1. Show whether the board improves the quality of OCM deliverables and decisions.
2. Show whether it speeds up first drafts and keeps deliverables consistent.
3. Show whether it accelerates the lead's professional growth.
4. Confirm that the guardrails and data protection rules work in practice.

### Choosing the engagement

A fictional engagement carries no client data risk and lets you test freely. A real engagement shows true value and surfaces practical constraints. If you choose a real engagement, prefer one in early stages, with a supportive sponsor and a lead who has completed phase 2 testing.

## Success criteria

Agree on the criteria and how they will be measured before the pilot starts. Collect a baseline from comparable past work where you can.

| Measure | Indicator | Target | Source |
|---|---|---|---|
| Quality | Reviewer rubric score on pilot deliverables | [target score] | Director or peer review |
| Quality | Fabrication incidents reaching client | Zero | Review log |
| Consistency | Conflicting assumptions found across deliverables at review | [target number] | Board Chair check, peer review |
| Practical value | Time to first draft for selected deliverables | [target reduction vs baseline] | Lead time log |
| Practical value | Decisions supported by board-prepared options | [target number] | Decision log |
| Growth | Lead self-assessment and director assessment | [target improvement] | Before-and-after review |

> **Tip:** Keep the measures few and the logging light. A pilot that takes more effort to measure than to run will not survive a busy engagement.

## Governance

| Role | Responsibility |
|---|---|
| Pilot sponsor ([Director, OCM]) | Approves the pilot, removes blockers, makes the scale decision |
| Pilot lead (OCM lead) | Runs the board, validates outputs, delivers to the client, keeps logs |
| Reviewer ([peer or senior practitioner]) | Scores sample outputs, checks for fabrication and consistency |
| Policy contact ([risk or privacy role]) | Confirms data handling and disclosure approach |
| Asset owner ([role]) | Maintains persona versions and the asset library |

Cadence:

- **Weekly:** pilot lead logs usage, issues, and time; reviewer scores a sample.
- **Every [number] weeks:** checkpoint with the sponsor on progress against success criteria.
- **End of pilot:** review against all criteria and a recommendation to stop, extend, or scale.

Any data-handling incident is reported immediately to the policy contact and the sponsor, and use pauses until it is resolved.

## Risks and mitigations

| Risk | Mitigation |
|---|---|
| Fabricated facts reach the client | Lead validation at every step; reviewer sampling; automatic-failure rule |
| Client data shared inappropriately | Approved tools only; pre-share checklist; anonymization routine |
| Over-reliance weakens the lead's judgment | Lead makes and records every decision; director coaching |
| Generic outputs that add little value | Complete Context Brief; persona testing; board challenge before delivery |
| Inconsistent assumptions across deliverables | Single versioned Context Brief; Board Chair consistency checks |
| Pilot effort competes with client delivery | Narrow scope; light logging; sponsor support |
| Results not comparable to past work | Agree baseline and measures before starting |

## The decision requested

Approve a pilot of the Agentic Board of Organizational Change Advisors on a [fictional or real] engagement, with:

- Scope: [advisors, stages, deliverables]
- Duration: [start date] to [end date]
- Pilot lead: [name]; Reviewer: [name]
- Success criteria as set out above, with targets confirmed by [date]
- A scale, extend, or stop decision at the end-of-pilot review on [date]

The board analyzes, drafts, and challenges. The OCM lead decides and delivers. The pilot will show whether that combination produces better decisions, faster and more consistent deliverables, and faster growth for the people who lead change.
